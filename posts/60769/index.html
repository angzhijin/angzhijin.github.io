Java中的一些Object模型

发表于2022-07-02|更新于2022-07-02|学习笔记
|字数总计:1.1k|阅读时长:3分钟|阅读量:

果然只有实习了，才会知道自己之前一个人写的代码是有多垃圾。

就比如说Java-Object在各个层级中的就使用着不同的模型，这种设计是在自己写，甚至是跟着教程写很难接触到的（至少我在实习前没有接触过）。

#分层领域模型

【参考】分层领域模型规约：

  • DO（Data Object）：此对象与数据库表结构一一对应，通过 DAO 层向上传输数据源对象。

  • DTO（Data Transfer Object）：数据传输对象，Service 或 Manager 向外传输的对象。

  • BO（Business Object）：业务对象，可以由 Service 层输出的封装业务逻辑的对象。

  • Query：数据查询对象，各层接收上层的查询请求。注意超过 2 个参数的查询封装，禁止使用 Map 类来传输。

  • VO（View Object）：显示层对象，通常是 Web 向模板渲染引擎层传输的对象。

    ——《阿里巴巴Java开发手册》

由于这些新概念都比较抽象，所以也是众说纷纭，甚至有不少概念间的区别很模糊，甚至是一样

这里借用一下知乎里一张关于分层领域模型的图示【1】，看了一圈算是解释的比较好的，但也有一些个人不是很认同。

个人觉得这种数据模型，从源头解释起会更容易理解

#POJO

POJO（Plain Old Java Objects，纯洁老式的Java对象），可以说是Java中的元老级概念了，我将其理解为以下所有模型的祖宗。

#DAO

DAO（Data Access Object，数据访问对象），这个也是接触的最多了，也就是直接与数据库对接的一个对象，一些地方也将其视作Mapper。

具体也就不多说了。

#PO

PO（Persistant Object，持久对象），这个概念见的较少，但用的挺多，可以视作Entity。

完全对应于数据库中的一条记录，其数据结构则对应数据库中表的结构。

一般只包含getter和setter方法

#DO

DO（Data Object，数据对象），直接对接自数据库，相当于上面的PO

#BO

BO（Business Object，业务对象），BO可以视作PO的组合，即相当于我的综合成绩是由语文、数学、英语等科目组成的，我的学籍档案是由高中、本科、研究生组成的一样，其中涉及一些业务处理。

#DTO

DTO（Data Transfer Object，数据传输对象），通常指前后端间的传输对象。

在前端，它的表现形式是json对象；在后端，它的表现形式是Java对象。（如何转换不需要操心，一般框架都会处理好）

#VO

VO（View Object / Value Object，视图对象 / 值对象），通常指返回给前端的展示数据。

很多时候，前端需要的数据并不是一个Entity中的所有字段，也不适合将所有字段暴露给前端，这时候就是要将其封装为一个VO，保证前端的业务需求，又不影响一些保留数据的暴露。

#一些补充

简单画了个转换，比较草率：

看了上面，其实不少概念都是比较类似甚至相同的，所以这里放一些补充说明，随着我水平不断提高不断学习，理解不断深入逐渐社畜，还会继续补充一些吧

  1. PO。这个必须有，也可以是叫Entity
  2. BO。在我理解来，BO是项目中中间处理的主体，但在我目前实习所写的接口中，似乎并没需要其的地方，可能还是在增删改查的阶段吧，基本上都是直接从Entity转VO了。
  3. VO和DTO。翻了不少文章，我理解上是VO只为视图服务，如前端页面，如果是给其他客户端、其他服务之后，还要进一步处理的，是看做DTO的。
  4. 至于各个层级中如何去使用，还是需要大量的经验，项目组间也可以讨论出个规约，有个规范总归是好事，大大提高代码可读性。
  5. 对于各个对象间的转换，可以通过写一堆繁杂的get/set方法来实现，也可以使用自定义Beans.copyProperties实现，最方便的还是通过MapStruct来转换呗
