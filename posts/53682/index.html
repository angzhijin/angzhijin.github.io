#版本控制系统

Version Control System

#本地版本控制系统

最流行的叫RCS，工作原理是保存补丁集（文件修订前后的变化）

#集中化版本控制系统

(Centralized VCS, CVCS)

  • CVS
  • Subversion
  • Perforce

缺点: 中央服务器故障或损坏, 导致无法工作甚至数据丢失

#分布式版本控制

(Distributed VCS, DVCS)客户端把代码仓库完整地镜像下来，包括完整地历史记录

  • Git
  • Mercurial
  • Bazaar
  • Darcs

#Git

#设计目标

  • 速度
  • 简单的设计
  • 对非线性开发模式的强力支持（允许成千上万个并行开发的分支）
  • 完全分布式
  • 有能力高效管理类似Linux内核一样的超大规模项目（速度和数据量）

#主要特性

  • 对待数据的方式
    • 基于快照（流）的VC
    • 其他：基于差异的VC
  • 本地执行
  • 完整性
    • 存储前计算校验和
    • 保存的信息都是以文件内容的哈希值（40个十六进制字符）来表示
  • 三种状态
    • 已修改（modified）
    • 已暂存（staged）
    • 已提交（committed）

#基本流程

  1. 工作区修改文件
  2. 将下次想要提交的更改选择性地暂存
  3. 提交更新，找到暂存区的文件，将快照永久性存储到Git目录

      • [abc]: 匹配任何一个在方括号中的字符

      • [0-9]: 匹配0-9任意一个数字
      • **: 匹配任意中间目录，如a/**/z 匹配 a/z, a/b/z, a/b/c/z等等
    • 匹配模式可以以 / 开头防止递归
    • 匹配模式可以以 / 结尾指定目录
    • 要忽略指定模式以外，可以在模式前加上 ! 取反

#查看提交历史

  • 常用选项
选项 说明
-p，--patch 按补丁格式显示每个提交引入的差异（-n 表示显示最近n次）
--stat 显示每次提交的简略统计信息
--shortstat 只显示--stat 中最后行数修改添加移除统计
--name-only 仅在提交信息后显示已修改的文件清单
--name-status 显示新增、修改、删除的文件清单
--abbrev-commit 仅显示SHA-1校验和中的前几个字符
--relativve-date 使用较短的相对时间（如 2 weeks age）
--graph 以ASCII码模拟显示分支与合并历史
-pretty= 使用其他格式显示历史提交信息
online: 将每个提交放在一行显示（浏览大量提交时可用）
short, full, fuller,
format：自定义提交格式
--online --pretty=online --abbrev-commit

  • git log --pretty=format：自定义显示格式

    • eg. git log pretty --pretty=format:"%h - %an, % ar : %s"

    • 常用选项

      选项 说明
      %H 提交的完整哈希值
      %h 提交的简写哈希值
      %T 树的完整哈希值
      %t 树的简写哈希值
      %P 父提交的完整哈希值
      %p 父提交的简写哈希值
      %an 作者name
      %ae 作者email
      %ad 作者修订日期（可使用--date=来定制格式）
      %ar 作者修订日期（距今时间）
      %cn 提交者name
      %ce 提交者email
      %cd 提交日期
      %cr 提交日期（距今时间）
      %s 提交说明

      作者：实际做出修改的人

      提交者：最后将工作成果提交到仓库的人

  • 限制输出长度

    • -<n>: 显示最近的n条提交
    • --since / --after: 显示指定时间后的提交（格式为2022-02-22 or 2.weeks）
    • --until / --before: 按时间限制
    • --author: 显示指定作者的提交
    • --committer: 显示指定提交者的提交
    • --greep: 包含关键字的提交
    • -S : 显示添加或删除内容匹配指定字符串的提交

  • 抓取和拉取

    git fetch从服务器上抓取本地没有的数据，且不会改变工作目录中的内容，只会获取数据然后让开发人员自己合并

    get pull在大多数情况下的含义是git fetch | git merge，会查找当前分支所跟踪的服务器与分支，从服务器上抓取数据然后尝试合并入哪个远程分支。

    由于pull的操作经常令人困惑，所以单独显式地使用fetch和merge会更好一些。

  • 跟踪分支

    克隆一个远程仓库的时候会自动创建一个跟踪origin/master的本地分支master
