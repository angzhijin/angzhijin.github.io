#认证和授权

  • 认证（Authentication）：验证身份
  • 授权（Authorization）：授予权限，发生在认证之后

#Cookie

#介绍

Cookie是用于跟踪浏览器用户身份的会话方式，与Session类似，但两者的应用场景不太一样。

Cookie是某些完整为了辨别用户身份二存储在用户本地终端上的数据（通常经过加密）。——维基百科

即：Cookie存放在客户端，一般涌来保存用户信息。

应用案例：

  1. 保存已经登录过的用户信息，还有用户首选项、主题和其他设置信息等
  2. 保存Session和Token，向后端请求时带上Cookie
  3. 记录分析用户行为

#使用

以Spring Boot 为例

  1. 设置Cookie返回给客户端

  2. 使用@CookieValue获取特定的Cookie值

  3. 读取所有Cookie值

#Cookie和Session

Session的主要作用是通过服务端记录用户的状态

  1. Cookie数据保存在客户端（浏览器），Session数据保存在服务器端。
  2. 相对来说Session安全性更高
  3. 最好将Cookie信息加密后使用时再去服务端解密

#使用Session-Cookie方案进行身份验证

SeesionID一般存放在Redis中

  1. 用户向服务器发送用户名、密码、验证码用于登录系统
  2. 服务器验证通过后，服务器为用户创建一个Session，并将Session保存起来
  3. 服务器向用户返回一个SessionID，写入用户的Cookie
  4. 但用户保持登陆状态时，Cookie将与后面每个请求一起被发送出去
  5. 服务器可以将存储在Cookie上的SessionID与存储在内存中或者数据库中的Seesion信息进行比较，以验证用户的身份，返回给用户客户端响应信息的时候会恢复带用户当前的状态。

使用Session时需要注意：

  1. 依赖Session的关键业务一定要确保客户端开启了Cookie
  2. 注意Session的过期时间

#多服务器节点下Session-Cookie方案

多服务器下，同一用户的不同会话可能分配给不同的服务器，此时不是每台服务器都有保存过对应的SessionID导致需要再次登录。

方案：

  1. 通过hash策略将同一用户的请求都分配给同一服务器。
  2. 每台服务器的Session信息互相同步（成本高）。
  3. 单独使用一个所有服务器都能访问的数据节点来保存Session信息。

#没有Cookie的话Session还能用吗

如果是使用Cookie保存SessionID的方案，客户端禁用Cookie后Session无法正常工作

但可以使用其他方式使用Session，比如说放在请求的url中，但安全性和用户体验性较差

#Token / JWT

JWT（JSON Web Token）是Token的实现。

本质上是一段签名的JSON格式的数据。由于其带有签名，因此接收者可以验证它的真实性。

JWT由三部分组成：

  1. Header：描述JWT的元数据，定义了生成签名的算法以及Token的类型
  2. Patload：用来存放实际需要传递的数据
  3. Signature签名：服务器通过Payload、Header和一个密钥使用Header里面指定的签名算法（默认是HMAC SHA256）生成

#

#基于Token进行身份验证

服务器通过Payload、Heder和一个密钥（secret）创建令牌（Token）并将Token发送给客户端，客户端将Token保存在Cookie或者LocalStorage里,以后客户端发出的所有请求都会携带这个令牌。

  • 可以放在Cookie中自动发送，但不能跨域
  • 更好的是放在HTTP Header 的Authorization字段中：Authorization: Bearer Token
  1. 用户向服务器发送用户名和密码用于登录系统
  2. 身份验证服务响应并返回了签名的JWT，散漫包含了用户是谁的内容
  3. 用户以后每次向后端发请求都在Header中带上了JWT
  4. 服务端检查JWT并从中获取用户相关信息

#Token认证的优势

  1. 无状态

    Token自身包含了身份验证所需要的所有信息，增加了系统的可用性和伸缩性，大大减轻了服务端的压力。

    但问题1也是由其造成的。

  2. 有效避免CSRF攻击

    1. CSRF（Cross Site Request Forgery），跨站请求伪造

      Hacker通过Cookie拿到其中的SessionId（如误点攻击链接）后代替用户访问系统。

      Token在成功登录获取之后，一般存放在LocalStorage中，通过某些方式给每个发送给后端的请求加上这个Token，这样就不会出现CSRF漏洞。

    2. XSS（Cross Site Scripting）跨站脚本攻击

      使用各种方式将恶意代码注入到其他用户的页面中。如通过脚本盗用Cookie等信息。

      无论是Cookie和Token都不发避免。

  3. 适合移动端使用

    Token可以被客户端存储就能使用，而且Token可以跨语言使用

  4. 单点登录友好

    Token被保存在客户端

#Token认证常见问题及解决方案

  1. 注销登录等场景下Token还有效

    Token派发出去如果后端不增加其他逻辑的话，它在是小钱都是有效的。

    解决方案

    • 将Token存入内存数据库（如Redis）。会导致每次请求都需要从DB中查询的步骤，且违背了JWT的无状态原则
    • 黑名单机制。使用内存数据库如Redis维护一个黑名单
    • 修改密钥
    • 保持令牌的有效期短并经常轮换。会导致用户的登录转台不会被持久记录，需要经常登录

    修改密码后解决token有效问题

    • 使用用户的米啊吗的哈希值对token进行签名

  2. Token续签问题

    • 类似于Session认证中的做法
    • 每次请求都返回新Token
    • Token有效期设置到半夜
    • 用户登录返回两个Token：accessToken和refreshToken

JWT 最适合的场景是不需要服务端潮纯用户状态的场景。

#SSO

  • 单点登录（SSO）的设计与实现 - Ken的杂谈

SSO（Single Sign On）即单点登录。

用户登录其中的一个就可以访问预期相关的其他系统。如京东下的各个APP

#好处

  • 用户角度：一次登录多次使用，无需记录多套用户名和密码，省心
  • 系统管理员角度：只需要维护一个统一的账号中心，方便
  • 新系统开发角度：新系统只需直接对接统一的账号中心，简化开发流程，省时

#设计目标

  • 单点登录
  • 单点登出
  • 支持跨域单点登录
  • 支持跨域单点登出

#设计与实现

  1. 核心应用与依赖

    前台站点、SSO站点、SSO服务、数据库、缓存

  2. 用户登录状态的存储和校验

    常见的Web框架对于Session的实现都是生成一个SessionId存储在浏览器Cookie中，然后将Session内容存储在服务端内存中。

    对于登录信息的存储，建议采用Redis，既保证高可用，又可以线性扩充，同时可以满足SSO负载均衡/可伸缩的需求。

  3. 用户登录/登录校验

  4. 用户登出

    • 服务端清除缓存中的登录状态
    • 客户端清除存储的AuthToken

  5. 跨域登录、登出

    跨域要解决的就是解决Cookie的跨域读写问题

    核心思路：

    1. 登录完成之后通过回调的方式，将AuthToken传递给主域名之外的站点，该站点自行将AuthToken保存在当前域下的Cookie中
    2. 登出完成之后通过毁掉的方式，通过非主域名站点的登出页面，完成设置Cookie中的AuthToken过期的操作
    3. 跨域登录（主域名已登录）

#OAuth 2.0

OAuth是一个行业的标准授权协议，主要用来授权第三方应用获取有限的权限。

OAuth2.0 是对OAuth1.0的完全重新设计，更快更易实现。

实际上是一种授权机制， 它的最终目的是为了第三方应用办法的一个有时效性的令牌Token，是的第三方应用能够通过该令牌获取相关的资源。

比较常用的场景就是第三方登录，但网站接入了第三方登录时一般就是使用OAuth 2.0 协议
